## 2. 구현·검증된 기능

- QUICK/R0 read-only 및 QUICK/R1 고정 한 파일·100행 범위, Executor coding profile, 필수 두 검증 단계와 executorDigest. R0의 known_risks는 정보성 finding으로 보존하며 완료를 막지 않지만 실제 changedFiles는 0이어야 한다. R1은 known_risks가 남으면 BLOCKED·STANDARD 재실행이 필요하다. 둘 다 unresolved 0·정확한 requirements/MET를 요구한다.
- STANDARD/R1·사전 선택한 R2의 독립 Developer/Reviewer, actual Git baseline/digest, PASS/REVISE/BLOCK 및 필수 check guards.
- R3의 사전 선택한 Git-tracked 일반 UTF-8 파일 한 개(256 KiB 이하) 삭제: 기본 Deny, exact/expiring/one-use consent, 소비 증거 및 독립 review/검증.
- 단일 writer, action intent/result, atomic file rename, partial persistence 오류, 관찰용 RuntimeEvent, 명시적 취소와 부분 변경 보고.
- 읽기 전용 observations와 명시적 generated export. 수동/수정 파일을 강제로 덮어쓰거나 export를 실행 권한으로 읽지 않는다.

| FIFO state/config/lock 파일이 open 단계에서 무한 대기 가능 | POSIX nonblocking/no-follow descriptor 열기와 regular-file 검사. config directory/file identity·크기 검사도 강화 |

### RC-01 — GPT QUICK/R0 completion semantics (2026-09-16 KST)

- **실제 Provider integration issue (사용자 보고):** disposable `weavra-rc-fixture`에서 `Explain src/calculator.js`를 실행했다. Provider/Worker 실행, 구조화 Executor 결과, SELF_CHECK/TEST가 정상이고 파일 변경도 없었지만, 기존 코드의 division-by-zero 미처리를 known_risks로 보고하자 `QUICK requirements incomplete or risks unresolved; STANDARD required`로 BLOCKED 됐다. 정확한 provider/model ID·비용/지연은 이번 보고에 없으며 추정하지 않는다.
- **원인:** Kernel `assertCanComplete()`가 모든 QUICK 작업에 `known_risks.length === 0`을 요구해 R0 설명에서 발견한 기존 코드의 위험을 미완료 작업과 혼동했다. 모델 실패나 fixture prompt 문제로 처리하지 않는다.
- **수정:** 검증된 `quickScope.risk === "R0"`일 때만 known_risks 완료 차단을 제외한다. finding은 executorResult/state에 보존한다. unresolved 0, 정확한 requirement coverage와 MET, 실제 changedFiles 0, SELF_CHECK/TEST/digest/state/scope guard는 유지한다. QUICK/R1 known risk는 계속 BLOCKED·STANDARD required이며 R2/R3/STANDARD completion guard는 변경하지 않았다. RC fixture·prompt·config는 수정하지 않았다.
- **수정 검증:** 수정 전 unit과 faux SDK 통합의 새 R0 사례가 같은 오류로 실패했고, 수정 후 COMPLETE/COMPLETED·무변경·finding 보존을 확인했다. R1 mutation+known risk는 양쪽 check PASS 후에도 BLOCKED·RunCompleted 미발행·STANDARD 안내를 유지한다. R0 known risk가 있어도 unresolved·미충족 requirements·실제 파일 변경·검증 실패·stale digest 등은 계속 차단하는 unit matrix를 실행했다.

### RC-04 — GPT STANDARD/R2 Reviewer evidence 참조 (2026-09-16 KST)

- **실제 Provider integration issue (사용자 보고):** Developer mutation과 SELF_CHECK는 성공했지만 Reviewer가 현재 verification에 없는 evidence ref를 제출했다. Adapter가 이를 수락해 세션을 끝낸 뒤 Kernel이 `Review references unknown or missing evidence`로 전체 run을 BLOCKED했다. 정확한 provider/model ID·비용/지연은 추정하지 않는다.
- **원인과 수정:** Reviewer JSON 입력에 `verification.evidenceRefs`와 `checks[].evidenceRefs`의 정확한 중복 제거 합집합인 `trustedEvidenceRefs`를 제공하고 prompt/tool 설명에서 그대로 복사하도록 명시했다. `submit_review`는 top-level 및 모든 requirement 참조를 이 집합과 비교한다. unknown/empty-required 참조는 결과로 수락하지 않고 Tool error로 반환한다. Adapter 내부에서 해당 call ID로 식별한 evidence 검증 오류만 세션 중단 대상에서 제외하여 같은 Reviewer 세션에서 재제출하도록 했다. 파일명·diffDigest·설명 문자열을 임의 참조로 만들거나 자동 보정하지 않는다.
- **유지한 guard:** Kernel `assertReview()`·freshness/integrity 및 completion semantics는 이번에 변경하지 않았다. 모든 verdict의 top-level ref는 1개 이상이며 PASS는 각 requirement에도 ref를 요구한다. REVISE/BLOCK은 requirement ref 배열이 비어 있어도 되지만 제공된 ref는 trusted set에 속해야 한다. identity/schema/권한 오류, 취소, timeout/turn limit, 혼합 tool submission은 기존 종료 조건을 유지한다. 기존 RC-01 작업 트리 변경도 보존했다.
- **자동 검증:** unknown top-level/requirement, missing required refs, filename/description/nonexact string/diffDigest-as-ref 거부와 같은 세션 retry, check-only ref의 정상 수락, REVISE/BLOCK 정책, retry 후 종료 경계를 검증했다. RC-04 유사 실제 Git/Policy/check + faux SDK 통합에서는 잘못된 review가 저장되지 않고 REVIEW/lock을 유지하다가 재제출 후 두 checks PASS·독립 두 세션·revision0·COMPLETED·unlock을 확인했다. 신규 **18개**다.

## 7. 보안·취소·commit 경계

- trusted local Host/Extension/Provider adapter/등록 check를 위한 협력적 gate다. 임의 Node 코드나 등록 프로그램의 내부 I/O를 가로채는 OS sandbox가 아니다.
- cleanup proof는 관리하는 SDK 작업과 원래 process group에 한정된다. `safeToRelease=false`면 FAILED/CANCELLED라는 Run label만 보고 lock을 지우면 안 된다. **worker/process 종료와 소유권을 수동 확인하기 전 추가 workspace 작업을 하지 않는다.** 자동 PID 기반 lock 탈취는 없다.
- custom AgentExecutor/Verifier는 promise 정산 전에 자원을 정리하거나 cleanup 미확인을 명시해야 한다. Pi/파일 adapter는 해당 상태를 구현한다. Runtime이 임의 외부 Port 구현의 정직성을 증명하지는 않는다.
- 정상 취소는 종료를 기다려 terminal state를 기록한 후 unlock한다. 정리가 불확실하면 실패 진단/기존 PREPARED intent만 남을 수 있고 lock을 유지한다. 이를 성공 또는 실행 안 됨으로 추정하지 않는다.
- cancel은 COMPLETE commit 시작 전까지 수락한다. 모든 guard를 통과해 terminal save가 시작된 뒤의 cancel은 늦은 요청이며 그 commit을 rollback하지 않는다. 저장 실패라면 RunCompleted를 발행하지 않는다. per-file partial commit으로 durable state와 caller 결과가 다를 가능성은 그대로다.
- R3 expiry는 effect 직전까지 검사한다. 실행 뒤 만료됐다고 승인된 effect를 되돌리거나 다시 실행하지 않는다. 재시작은 미완료 grant/action을 INTERRUPTED로 남긴다.
- RuntimeEvent는 best-effort 관찰이다. emit 오류는 별도 진단이며 완료/실패를 재판정하지 않는다. outbox/replay/exactly-once 전달은 없다.

## 8. 알려진 위험과 미지원 기능

- 비협조 Provider/auth/event sink/파일 I/O는 cancellation/shutdown을 오래 지연시킬 수 있다. timeout은 강제 OS 종료의 절대 기한이 아니며 이 경우 lease를 유지한다.
- 뜻밖의 SDK 생성/cleanup 또는 process runner 예외는 실제 자원이 없었어도 보수적으로 lease를 남길 수 있다. 자동 해제보다 수동 확인을 우선한다.
- status/read-only snapshot은 live filesystem 검증이나 프로세스 생존 증명이 아니다. 오래된 PASS·partial state/tasks·메모리 전용 진단 손실을 함께 해석해야 한다.
- 실제 effect와 durable result 사이에는 transaction이 없다. 승인된 삭제나 write 뒤 저장 실패가 남을 수 있다. 자동 rollback/checkpoint/resume 없음.
- risk/요구사항 판정은 heuristic·모델 판단·등록 check 품질에 의존한다. semantic safety의 수학적 증명, 모든 secret/manifest 탐지, credential-free stdout 보장은 없다.
- 파일/출력/state 크기 제한과 보수적 경로 거부, dirty baseline 거부, export 수동 소유권 충돌은 유지된다. generated checksum은 인증 서명이 아니다.
- UNSUPPORTED: Lead/Planner·COMPLEX 실행·parallel agents·generic R3·arbitrary shell·deploy/install 권한 확대·DAG scheduler/renderer·T3Code·RPC/Web UI·auto resume/checkpoint·model fallback/cost routing·SQLite·신규 OS sandbox·패키지/브랜딩 migration.
- 전체 테스트/build, live Provider 및 dependency vulnerability 재평가는 이번에 실행하지 않았다. 과거 WORK_LOG의 dependency audit를 현재 보안 통과로 주장하지 않는다.

## 9. RC 진입 판정

**조건부 가능:** 제한된 지원 범위에서 로컬 faux·실제 파일/process·선택한 Pi 회귀와 interactive 실패 경계를 검증했다. 위 PARTIAL/UNSUPPORTED/NOT VERIFIED를 사용자에게 그대로 공개해야 한다.

다음 RC gate는 별도 승인 후 수행한다: 실제 GPT/DeepSeek disposable-project smoke, 선택 모델/auth/env 확정, 지원할 OS/Node 버전 검증, 프로젝트별 build/lint/test 검증, 패키지 취약점·배포/설치 검증 범위 결정. S6 결과만으로 V0.1 release/일반 production 안전성을 선언하지 않는다.
